# Casio FP-1100 target

`make fp1100` builds `build/fp1100/simcity.d88`, a boot disc for the FP-1100 with the uPD765A floppy pack. There is no CP/M and no BASIC: the machine's ROM reads the
boot sector, and everything after that is the game's. It is built by z88dk (`zcc +fp1100 -subtype=allram ... -create-app -Cz"--data build/fp1100/art.bin"`):
z88dk's fp1100 crt, bootstrap, library and `appmake +fp1100`.

## The machine, as the game uses it

* A Z80 with 64 KB, all of it RAM once the ROM's copy of itself (RAM at `$0000`-`$8FFF`) is overwritten. The ROM is switched off by the boot sector's reads (port `$FFA0` bit 1 keeps RAM mapped).
* The screen belongs to a uPD7801 sub-CPU. Video RAM is three planes (blue, red, green) at sub addresses `$2000`, `$6000`, `$A000`, 40x25 cells of 8 bytes each (a byte is a line, the leftmost
  pixel is bit 0), 320x200 in 8 colours. The sub-CPU's bus inverts what it reads and writes: a direct write of W shows as ~W, and a copy inside the video RAM (a read then a write)
  flips each byte. Pictures are stored raw and copied, so they come out as stored.
* The Z80 talks to the sub-CPU through ports `$FFC0` (a byte) and `$FF80` (INT2 to the sub-CPU: `$C0` then `$20`; the sub-CPU's ready flag comes back in bit 7). Every byte is a handshake
  of about 0.4 ms in MAME, so the cost of a drawing is roughly the bytes sent, and the sub-CPU is slow (a tile copy is about 0.8 ms).
* The floppy pack is a uPD765A at the slot chosen by ports `$FFA0` and `$FF00`; ports 0 (motor), 2 (terminal count), 4 (main status) and 5 (data). It is driven polled, in non-DMA mode.

## Boot

1. The ROM reads track 0 sector 1 to `$9000` and runs it (z88dk's `BOOTSTRAP` section).
2. That reads 8 sectors with the ROM's sector read (`$0356`, still in RAM at that point) to `$F800` and jumps there (`BOOTSTRAP2`, the loader).
3. The loader has its own copy of the polled disc driver (`lib/target/fp1100/classic/fp1100_disk.inc`, the same source as z88dk's `fp1100_disk_read`/`fp1100_disk_write`), reads the program
   from sector 9 to `$0000` (the ROM's routines are overwritten), and jumps to it.
4. The program's `plat_init` calls `fp_boot` (`fp_sub.asm`), which takes the sub-CPU over. The ROM's sub-CPU program takes a loader through its "define character" command; the Z80's end is the
   ROM's own transport: a byte on `$FFC0`, `$90` then `$10` to `$FF80`, and the sub-CPU's answer comes back as the INTS interrupt (interrupt mode 2, vector `$F0`, a table at `$FFF0`; interrupts
   are on only while waiting for it). The loader then brings in the real sub program (`sub.s.in`, two pages at `$9000` and `$9100`) through the program's own handshake.
5. `fp_art` reads the pictures from the disc (the extra block after the program) and sends them to the sub-CPU, 32 at a time through a buffer on the stack.

## The disc

Logical sector n is track n / 16 (track = 2 * cylinder + side), sector id n % 16 + 1; the sectors of a track are interleaved 1, 9, 2, 10, ... so that the polled loops have time to ask for the next.

| Sectors | |
|---|---|
| 0 | boot sector |
| 1-8 | loader |
| 9 on | the program, then the pictures (`art.bin`: 457 pictures of 24 bytes, padded to sectors) |
| from track 24 (sector 384) | 8 save slots of 3 tracks: sector 0 of a slot is the game block with the city's name in its first 12 bytes and `SC` in the last two, the map after it (the same scheme as the X1's) |

`make fp1100` stops if the program and pictures reach sector 384. Saving writes the map before the header, so a half-written slot is not listed.

## Memory

* Z80: the program and its constants `$0000`-`$9E82` (about 40 KB), the uninitialised data from there to `$F05C`, the stack down from `$FFF0` (2 KB: the build stops if the data goes past `$F800`).
* Sub-CPU: the sub program at `$9000` (page 1, the commands' entry points, 256 bytes at most) and `$9100` (page 2, the long commands); pictures as 32-byte slots (blue, red, green, 8 spare):
  bank 0 `$4000` (pictures 0-255), bank 1 `$8000` (256-344), bank 2 `$C000`: the font's glyphs (code * 32; the space at `$C400` serves for blanking) and from `$D000` the 112 cells of the tool icons
  (normal and dimmed, made by `tools/fp1100_art.py` from `assets/cpc_icons.bin`).

## Drawing

The Z80 keeps what is on the screen and sends as little as possible:

* the map: `fp_cache` has the picture of every map cell, so a cell that shows what is wanted costs nothing; changed cells are queued as runs of adjacent pictures and sent as one `Tiles` command (a picture
  is one byte; `fp_tile.asm` adds to the run in assembler);
* text: `fp_txt` has each cell's character; a run of characters goes as one `Text` command with an attribute (ink and paper colours), drawn from the glyphs by the sub-CPU; the status panel keeps a checksum
  per cell (`cell_sum`) so a redraw of unchanged cells sends nothing;
* the tool icons are stored pictures (`Tiles` from bank 2, the selected one flipped by `Inv`); the demand bars are composed on the Z80 and sent whole;
* `plat_clear` is `Fill` (blank cells copied from the space glyph) and is skipped when the screen is already blank;
* mini maps: `plat_put_minirow` packs a row of tiles (2x2 pixels, 4 tiles to a byte, the density maps' dim checker) and sends it as `Mini`/`Mini2`.

The sub program's commands (`sub.s.in`): Bank, Addr, Pat, Cell, Ovl, Tiles, Inv, Keys, Tick, Fill, Text, Mini, Mini2. `Keys` scans the key matrix; `Tick` returns the sub-CPU timer's overflows (about 0.67 ms each)
since the last call, which is the game's only clock: a frame is 30 of them.

Speed (MAME): a full redraw such as leaving the budget is about 1.8 s (760 map tiles are about 0.6 s of the sub-CPU's copying alone), a mini map 5-6 s.

## Not done

No sound (the beeper is a click, not a tone generator), no scenarios, no hardware scroll (the map redraws tile by tile; the sub-CPU could blit), no mini map panning (the map is 96x96 so it is
not needed).

## Tests (`test/fp1100/`)

* `disk_test.py`, `files_test.py`, `stage2_test.py`: the polled driver (register and C entries), save/load, and the loader, under `z88dk-ticks` against a uPD765A model (`fdc_model.lua` on
  `lib/ticks/upd765.lua` in z88dk). The model has no clock, so timing is not checked.
* `fp_machine.lua` and `headless.py`: the whole game under ticks, with the sub-CPU's commands modelled, a key schedule and PNG screenshots (`render.py`), about a second for 400 frames. The ROM's sub-CPU
  program is not modelled, so `fp_boot` is patched out.
* `game_run.lua`: the game in MAME (`-video none`), with the real sub-CPU running the sub program. MAME has no floppy pack, so it writes the pictures into the sub-CPU's RAM and patches `fp_art` out;
  the takeover is the real one.
* Checked on the Takeda emulator by hand: boot, the takeover, keys, save and load, icons.
